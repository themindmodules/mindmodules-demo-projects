# 24-hour plan

| Hours | Goal | Done when |
|---|---|---|
| 0-1 | Agree the problem, split roles, create the repo | Everyone has the repo and knows their task |
| 1-3 | Talk to two teachers or class reps at the venue | Two real quotes written in `PROBLEM.md` |
| 1-5 | Token and rules: `common.py`, `analyze.py`, `check_rules.py` | Self-test passes |
| 3-7 | Simulator with injected cases | Every injected case is caught, honest students marked |
| 5-10 | Dashboard: tiles, class grid, flags table | Opens from `file://`, readable on a projector |
| 10-12 | Code display page (laptop) that rotates the QR every 15 s | Phone camera reads it from 8 m |
| 12-14 | Break and sleep in shifts. Do not skip this. | Team is functional again |
| 14-18 | Optional: scanning web page posting rows to a small server | One real scan appears in the CSV |
| 18-20 | Pitch slides and demo rehearsal | Two full run-throughs with a timer |
| 20-22 | Bug fixing only. Feature freeze at hour 20. | No new features |
| 22-23 | Final rehearsal, backup video, screenshots | Backup video recorded |
| 23-24 | Submit, charge laptops, test the projector adapter | Submission confirmed |

## Rules that save hackathons

1. **Feature freeze at hour 20.** Late features break demos.
2. **Record a backup demo video** at hour 22. Venue Wi-Fi fails.
3. **Test the QR from the back of the room** on the real projector, not just your laptop screen.
4. **Commit often.** If a laptop dies, you still have the repo.
